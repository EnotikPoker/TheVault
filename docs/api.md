# HTTP API

Базовый путь: `/api`. Успешные ответы и ошибки игровых методов возвращаются
в JSON с `Cache-Control: no-store`. Даты — UTC, прошедшее время — миллисекунды.

## Проверка сервера

`GET /api/health` возвращает `200 OK`:

```json
{"status":"ok"}
```

## Игровые методы

| Метод и путь | Результат |
| --- | --- |
| `POST /api/v1/vaults` | Новая сессия, `201 Created` |
| `GET /api/v1/vaults/{id}` | Состояние и история сессии, `200 OK` |
| `POST /api/v1/vaults/{id}/checks` | Проверка комбинации и обновлённое состояние, `200 OK` |

Все три метода возвращают одинаковую модель состояния. ID сессии и seed создаются
на сервере через `crypto/rand`. Seed и объект сейфа в ответы не попадают.
Сессии существуют в памяти одного процесса до его остановки; авторизации пока нет.

### Создание сессии

`POST /api/v1/vaults` принимает пустое тело или `{}`. Параметры, включая `seed`,
не поддерживаются. Заголовок `Location` содержит путь созданной сессии.

Пример начального состояния:

```json
{
  "id": "69376fb01da74c3591d30245f35da834",
  "createdAt": "2026-10-28T10:00:00Z",
  "status": "locked",
  "attempts": 0,
  "elapsedMs": 0,
  "switches": null,
  "indicators": [
    {"id": "power", "passed": null},
    {"id": "sync", "passed": null},
    {"id": "access", "passed": null}
  ],
  "history": []
}
```

`switches` — последняя проверенная комбинация в порядке S1–S5. До первой проверки
она равна `null`, а индикаторы имеют нейтральное значение `passed: null`.
Поля `openedAt` и `explanations` отсутствуют до открытия.

### Проверка комбинации

Тело `POST /api/v1/vaults/{id}/checks`:

```json
{"switches":[true,false,true,false,false]}
```

Поле обязательно и должно содержать ровно пять JSON-значений `boolean`.
`null`, числа, строки, лишние поля и данные после JSON-объекта отклоняются.
Максимальный размер тела запросов создания и проверки — 4 KiB.

Принятая проверка увеличивает `attempts` на один и обновляет `switches`
и `indicators`. `passed: true` означает, что условие системы выполнено,
`passed: false` — что не выполнено. Повторная проверка той же комбинации
расходует новую попытку. Автоматических повторов и защиты от повторной отправки нет.

В `history` сохраняется каждая принятая проверка. Например, одна запись:

```json
{
  "attempt": 1,
  "switches": [true, false, true, false, false],
  "indicators": [
    {"id": "power", "passed": true},
    {"id": "sync", "passed": false},
    {"id": "access", "passed": true}
  ],
  "elapsedMs": 1500
}
```

Это пример формата, а не фиксированные правила сейфа. Время считается от создания
сессии. История упорядочена по номеру попытки. `GET` возвращает её целиком, поэтому
по ID можно восстановить игру после обновления страницы.

### Открытие

Когда все индикаторы проходят проверку, `status` становится `opened`,
в ответ добавляются `openedAt` и массив из трёх `explanations`. Каждое объяснение
содержит `id` системы, `condition` с условием и `observation` с фактическими
положениями переключателей.

Время решения фиксируется: последующие `GET` возвращают неизменный `elapsedMs`.
Новые проверки отклоняются и не меняют историю или счётчик. Параллельные проверки
обрабатываются атомарно: единственный запрос открывает сейф, последующие получают
`409`.

## Ошибки

Пример ошибки игрового метода:

```json
{"error":{"code":"not_found","message":"Session not found."}}
```

| HTTP | Код | Причина |
| --- | --- | --- |
| `400` | `invalid_request` | Неверное или слишком большое тело запроса |
| `404` | `not_found` | Сессия не найдена |
| `409` | `already_opened` | Сейф уже открыт |
| `500` | `internal_error` | Внутренняя ошибка без технических подробностей |

Ошибка не расходует попытку. Для неизвестных маршрутов и неподдерживаемых методов
стандартные `404` и `405` формирует `net/http`; их тела не используют JSON-формат
игровых ошибок.
