# HTTP API

Базовый путь: `/api`. Успешные ответы и ошибки игровых методов возвращаются
в JSON с `Cache-Control: no-store`. Временные метки — UTC, прошедшее время — миллисекунды.

## Проверка сервера

`GET /api/health` возвращает `200 OK`:

```json
{"status":"ok"}
```

## Сканер Black Box

| Метод и путь | Результат |
| --- | --- |
| `GET /api/v1/blackbox/daily` | Дата текущего сейфа и время смены, `200` |
| `POST /api/v1/blackbox/sessions` | Новая сессия, `201`, `Location` |
| `GET /api/v1/blackbox/sessions/{id}` | Полное публичное состояние, `200` |
| `PUT /api/v1/blackbox/sessions/{id}/scans/{side}/{index}` | Сканирование порта, `200` |
| `PUT /api/v1/blackbox/sessions/{id}/marks` | Полная замена отметок, `200` |
| `POST /api/v1/blackbox/sessions/{id}/answers` | Проверка расположения, `200` |

Сессии сканера сохраняются в PostgreSQL. Авторизации нет: ID сессии даёт доступ
к её состоянию и действиям. ID и seed создаются сервером; seed не возвращается.
Неизвестные поля, неверные координаты и тела запросов отклоняются с `400`.
Лимит тела — 4 КиБ.

### Сейф дня и создание

`GET /api/v1/blackbox/daily` не создаёт сессию или головоломку:

```json
{
  "date": "2026-10-28",
  "resetsAt": "2026-10-28T21:00:00Z",
  "size": 6,
  "elementCount": 3
}
```

Дата дня определяется в `Europe/Moscow`, смена — в местные 00:00.
Начатая сессия остаётся доступна после полуночи. Каждая сессия имеет свой прогресс;
ежедневные сессии одной даты используют общую раскладку.

Создание принимает `{"mode":"daily"}` или `{"mode":"practice"}`.
Начальное состояние:

```json
{
  "id": "69376fb01da74c3591d30245f35da834",
  "mode": "daily",
  "date": "2026-10-28",
  "size": 6,
  "elementCount": 3,
  "rulesVersion": 1,
  "status": "locked",
  "createdAt": "2026-10-28T10:00:00Z",
  "elapsedMs": 0,
  "scanCount": 0,
  "wrongAnswers": 0,
  "score": 0,
  "marks": [],
  "scans": [],
  "answers": []
}
```

У тренировки `mode` равен `practice`, поля `date` нет.
`score = scanCount + 5 * wrongAnswers`. Все игровые методы возвращают полное
состояние. Время считается от создания до открытия сессии.

### Сканирование

`side`: `top`, `right`, `bottom`, `left`; `index`: от `0` до `5`.
Верхние и нижние порты нумеруются слева направо, боковые — сверху вниз.
В UI им соответствуют N1–N6, S1–S6, E1–E6 и W1–W6.
Тело запроса пустое или `{}`.

В `scans` добавляется запись:

```json
{
  "number": 1,
  "entry": {"side":"top","index":0},
  "result": {"kind":"exit","exit":{"side":"bottom","index":0}},
  "elapsedMs": 1250
}
```

`result.kind`: `hit` (поглощение), `reflection` (возврат в исходный порт),
`exit` (другой порт). Поле `exit` есть только в последнем случае.
Повторный вход или вход в выход уже записанной пары возвращает состояние
без увеличения счётчика. Это работает и после вскрытия. Новый скан открытого
сейфа даёт `409 already_opened`.

### Отметки

Координаты `row`, `col` — целые от `0` до `5`, начало в левом верхнем углу.
`PUT /marks` заменяет весь список; `{"marks":[]}` очищает его.

```json
{"marks":[{"row":0,"col":2,"state":"suspected"},{"row":1,"col":2,"state":"empty"}]}
```

Одна отметка на клетку, не более трёх `suspected`. Отметки не влияют на очки
и не проверяют скрытую раскладку. После вскрытия изменение запрещено.

### Ответ и повтор после сбоя

```json
{
  "requestId": "e02fc3301f124012ac82f600a966de2e",
  "cells": [{"row":0,"col":2},{"row":3,"col":4},{"row":5,"col":0}]
}
```

Требуются три различные клетки. `requestId` — 16 случайных байт в hex,
32 символа. Один ID обозначает одну проверку; порядок клеток не влияет.
Повтор ID с теми же клетками не добавляет ответ и штраф, включая повтор после
вскрытия. Другие клетки с тем же ID дают `409 request_conflict`.
Новый ID при неверном расположении увеличивает `wrongAnswers` на один.
Неверный ответ — успешный HTTP `200`, статус сессии остаётся `locked`.
Число совпавших клеток не возвращается.

В `answers` записывается история собственных проверок:

```json
{"requestId":"e02fc3301f124012ac82f600a966de2e","cells":[{"row":0,"col":2},{"row":3,"col":4},{"row":5,"col":0}],"correct":false}
```

Клиент сохраняет ID и клетки до отправки. После потери ответа делает GET:
если `requestId` есть в `answers`, запрос обработан; иначе можно повторить тот же
POST. Нельзя создавать новый ID только из-за потери ответа.

### Вскрытие и ошибки

Правильный ответ переводит сессию в `opened` и добавляет `openedAt`,
`solution` (три клетки) и `path` у каждого сканирования. `path` — упорядоченный
список координат, включая вход и конечную точку. Координата за полем может быть
`-1` или `6`. У отражения перед входом путь состоит из одной внешней точки.
До вскрытия ни `solution`, ни `path` не передаются.

После открытия время фиксировано. Новые ответы и отметки запрещены;
идемпотентные повторы ранее обработанных ответов остаются допустимыми.

| Статус | Код | Причина |
| --- | --- | --- |
| `400` | `invalid_request` | Неверное тело, координаты, режим, порт или ID проверки |
| `404` | `not_found` | Сессии нет |
| `409` | `already_opened` | Новое действие после открытия |
| `409` | `request_conflict` | ID проверки повторён с другими клетками |
| `500` | `internal_error` | Ошибка обработки или БД, внутренние детали не возвращаются |

## Переключатели

| Метод и путь | Результат |
| --- | --- |
| `POST /api/v1/vaults` | Новая сессия, `201 Created` |
| `GET /api/v1/vaults/{id}` | Состояние и история сессии, `200 OK` |
| `POST /api/v1/vaults/{id}/checks` | Проверка комбинации и обновлённое состояние, `200 OK` |

Все три метода возвращают одинаковую модель состояния. ID сессии и seed создаются
на сервере через `crypto/rand`. Seed и объект сейфа в ответы не попадают.
Сессии существуют в памяти одного процесса до его остановки; авторизации пока нет.

### Создание сессии

`POST /api/v1/vaults` принимает пустое тело или `{}`. Параметры, включая `seed`,
не поддерживаются. Заголовок `Location` содержит путь созданной сессии.

Пример начального состояния:

```json
{
  "id": "69376fb01da74c3591d30245f35da834",
  "createdAt": "2026-10-28T10:00:00Z",
  "status": "locked",
  "attempts": 0,
  "elapsedMs": 0,
  "switches": null,
  "indicators": [
    {"id": "power", "passed": null},
    {"id": "sync", "passed": null},
    {"id": "access", "passed": null}
  ],
  "history": []
}
```

`switches` — последняя проверенная комбинация в порядке S1–S5. До первой проверки
она равна `null`, а индикаторы имеют нейтральное значение `passed: null`.
Поля `openedAt` и `explanations` отсутствуют до открытия.

### Проверка комбинации

Тело `POST /api/v1/vaults/{id}/checks`:

```json
{"switches":[true,false,true,false,false]}
```

Поле обязательно и должно содержать ровно пять JSON-значений `boolean`.
`null`, числа, строки, лишние поля и данные после JSON-объекта отклоняются.
Максимальный размер тела запросов создания и проверки — 4 KiB.

Принятая проверка увеличивает `attempts` на один и обновляет `switches`
и `indicators`. `passed: true` означает, что условие системы выполнено,
`passed: false` — что не выполнено. Повторная проверка той же комбинации
расходует новую попытку. Автоматических повторов и защиты от повторной отправки нет.

В `history` сохраняется каждая принятая проверка. Например, одна запись:

```json
{
  "attempt": 1,
  "switches": [true, false, true, false, false],
  "indicators": [
    {"id": "power", "passed": true},
    {"id": "sync", "passed": false},
    {"id": "access", "passed": true}
  ],
  "elapsedMs": 1500
}
```

Это пример формата, а не фиксированные правила сейфа. Время считается от создания
сессии. История упорядочена по номеру попытки. `GET` возвращает её целиком, поэтому
по ID можно восстановить игру после обновления страницы.

### Открытие

Когда все индикаторы проходят проверку, `status` становится `opened`,
в ответ добавляются `openedAt` и массив из трёх `explanations`. Каждое объяснение
содержит `id` системы, `condition` с условием и `observation` с фактическими
положениями переключателей.

Время решения фиксируется: последующие `GET` возвращают неизменный `elapsedMs`.
Новые проверки отклоняются и не меняют историю или счётчик. Параллельные проверки
обрабатываются атомарно: единственный запрос открывает сейф, последующие получают
`409`.

## Ошибки

Пример ошибки игрового метода:

```json
{"error":{"code":"not_found","message":"Session not found."}}
```

| HTTP | Код | Причина |
| --- | --- | --- |
| `400` | `invalid_request` | Неверное или слишком большое тело запроса |
| `404` | `not_found` | Сессия не найдена |
| `409` | `already_opened` | Сейф уже открыт |
| `500` | `internal_error` | Внутренняя ошибка без технических подробностей |

Ошибка не расходует попытку. Для неизвестных маршрутов и неподдерживаемых методов
стандартные `404` и `405` формирует `net/http`; их тела не используют JSON-формат
игровых ошибок.
