# Архитектура

## Общая схема

```text
Браузер: React + TypeScript + Vite
          │ HTTP / JSON
          ▼
Go: transport/httpapi → session → vault
                          │
                          ▼
                   интерфейс хранилища
                          │
                          ▼
                  память процесса (MVP)
```

Сейчас реализованы HTTP health endpoint, клиент проверки связи, макет панели
и отдельное игровое ядро `vault`. Игровые маршруты и пакет `session` ещё не добавлены.

## Backend

`cmd/server` отвечает за запуск, конфигурацию через окружение, таймауты
и корректное завершение по сигналам. `internal/transport/httpapi` переводит
HTTP-запросы в вызовы сценариев и сериализует ответы.

Пакет `internal/vault` хранит модель, вычисляет результат правил и генерирует сейфы.
Он не зависит от транспорта, базы данных и UI. Правила закрыты для изменения,
проверки не меняют сейф и допускают параллельные вызовы.

Интерфейс ядра:

- `Generate(seed int64) (Vault, error)` — сейф с единственным решением.
- `Vault.Check(Combination) CheckResult` — три индикатора и признак открытия.
- `Vault.Explain(Combination) ([3]Explanation, error)` — условия и фактические
  положения переключателей для решения; иначе `ErrVaultLocked` без объяснений.

`Combination` — массив из пяти `bool` в порядке S1–S5. Результаты содержат
идентификаторы `power`, `sync`, `access`. Нулевое значение `Vault` остаётся закрытым.
Ядро не считает попытки, не хранит время и не запоминает факт предыдущей проверки.

Генератор один раз строит каталог правил, сравнивает их поведение на всех
32 комбинациях и исключает дубликаты. Из троек правил отбираются только наборы
с одним решением, участием всех переключателей и необходимостью каждого индикатора.
Равновероятно выбирается одна допустимая тройка, затем перемешивается назначение
индикаторам. Каталог хранится в памяти процесса, генератор случайных чисел
создаётся отдельно для каждого вызова.

Одинаковый seed воспроизводит сейф при неизменной версии ядра. Совпадения между
разными seed допустимы. Seed служит для воспроизведения и не должен передаваться
игроку до решения. Публичные HTTP-ответы в будущем должны собираться отдельно
от модели `Vault`.

Будущий пакет `internal/session` реализует создание сессии, проверку комбинации,
учёт попыток и времени, выдачу объяснения после открытия. Он определяет интерфейс
хранилища; адаптер в памяти будет добавлен с первым игровым сценарием.
Модификации сессии должны быть атомарными, включая параллельные проверки.

Сервер — источник истины для правил, результатов, числа попыток и времени.
Публичные DTO отделяются от внутренней модели: seed и правила не должны попадать
в ответы до открытия, в том числе через общий JSON-сериализатор модели.

## Frontend

`src/main.tsx` монтирует React-приложение в `StrictMode`. `src/app/App.tsx`
собирает экран и проверяет соединение с сервером через `useEffect`, отменяя
запрос при размонтировании. `src/features/vault/VaultPanel.tsx` содержит панель
и хранит положения переключателей в `useState`. В дальнейшем компонент будет
отображать результаты и журнал проверок. `src/shared/api` содержит обращения
к серверу и обработку ответов.

При подключении игрового API редактируемую комбинацию нужно хранить отдельно
от последней проверенной. Кнопка проверки будет блокироваться на время запроса,
а счётчик и итоговое состояние — приходить из ответа backend.

Интерфейс описан React-компонентами на TypeScript (`.tsx`). Vite использует
официальный React-плагин для разработки с Fast Refresh и сборки.
Зависимости зафиксированы в lock-файле.

## Хранение и запуск

Начальный MVP предполагает хранилище в памяти: перезапуск сервера сбрасывает
сессии. Постоянное хранение и авторизация добавляются при появлении требований
к восстановлению прогресса, аккаунтам или таблице результатов.

В разработке Vite проксирует `/api` на Go. Production-раздача статических файлов
и reverse proxy будут настроены отдельным этапом. Docker, база данных и очереди
не требуются для текущего каркаса.
