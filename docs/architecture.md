# Архитектура

## Общая схема

```text
React + TypeScript + Vite
            │ HTTP / JSON
            ▼
     transport/httpapi
       │           │
       ▼           ▼
 blackboxgame    session
   │      │       │     │
   ▼      ▼       ▼     ▼
blackbox postgres vault MemoryStore
            │
            ▼
       PostgreSQL 18
```

Backend контролирует скрытые данные, результаты, очки и время. Frontend создаёт
сессии только по действию игрока, ставит отметки и отображает серверные снимки.
Сканер и переключатели имеют отдельные сервисы, API и браузерные ключи хранения.

## Сканер

`internal/blackbox` не зависит от HTTP, БД и часов. `Board` хранит 36-битную маску
из трёх занятых клеток. `Trace(Port)` возвращает исход и полный путь луча.
Правила имеют версию; текущая — `1`. Поглощение важнее диагонального отклонения,
у края отдельно проверяется отражение до входа. Защита от повторного состояния
не допускает бесконечного вычисления пути.

При первом вызове генератор перебирает 7140 раскладок из трёх элементов.
Для каждой вычисляет сигнатуру исходов всех 24 портов. Все участники групп
с одинаковой сигнатурой исключаются, а не выбирается один представитель:
иначе игрок не смог бы отличить правильный ответ от другого допустимого.
В каталоге остаётся 7116 различимых раскладок. Это гарантирует различимость
при полном наборе наблюдений, но не задаёт сложность отдельной головоломки.
`Generate(seed)` воспроизводим в пределах версии правил; публичного seed нет.

`internal/blackboxgame` реализует создание ежедневной и случайной сессии,
сканирование, замену отметок, проверку ответа и выдачу состояния. Часы,
генератор и ID подменяются через `Options` в тестах. ID и случайный seed
в обычном запуске создаются через `crypto/rand`.

Публичный `Snapshot` отделён от внутренней сессии. Пока сейф закрыт, в нём нет
раскладки и путей лучей. Он содержит отметки, исходы сканирований и историю
собственных ответов. При успехе сервис фиксирует `OpenedAt`, возвращает `solution`
и пересчитывает пути записанных лучей. Время после открытия не растёт.

Повторный вход в известный порт или в выход ранее записанного луча не создаёт
сканирование. Ответы имеют `requestId`: повтор того же ID с теми же клетками
возвращает состояние без нового штрафа; другое содержимое даёт конфликт.
Правильность определяется всем набором клеток без раскрытия частичных совпадений.

## PostgreSQL

`internal/postgres` реализует интерфейс `Repository` сервиса сканера через pgxpool.
`blackbox_puzzles` хранит маску, версию правил и необязательную дату.
Уникальный `puzzle_date` фиксирует одну раскладку для всех сессий этого дня;
у тренировок дата равна `NULL`. `blackbox_sessions` связывает непрозрачный ID
с головоломкой и хранит состояние сессии в JSONB. Маска не дублируется в JSON.

Создание головоломки и сессии выполняется одной транзакцией. Конкурирующие
создатели сейфа дня используют `ON CONFLICT` и читают уже записанную раскладку.
Изменения сессии выполняются под `SELECT ... FOR UPDATE`: параллельные сканы
и повторы ответов видят последовательное состояние. Ошибка callback откатывает
изменения. JSON декодируется заново при чтении; хранилище не отдаёт общие ссылки.

Дата дня определяется сервером в `Europe/Moscow`, временные метки хранятся в UTC.
Начатая до полуночи сессия остаётся связана со своим днём и доступна для решения.

SQL-миграции встроены в Go-бинарник и применяются на старте в транзакции
под общей advisory lock. Применённые версии записаны в `blackbox_schema_versions`.
Сервер не запускается без `DATABASE_URL` или доступной БД; подмены хранилищем
в памяти нет. Авторизации, срока хранения и фонового удаления сессий пока нет.

## Переключатели

`internal/vault` содержит четыре вида правил, генерацию сейфа с единственным
решением среди 32 комбинаций и объяснения после вскрытия. `internal/session`
считает попытки и время, хранит историю в `MemoryStore` под mutex. Каждая принятая
проверка, включая повторную комбинацию, увеличивает число попыток. Перезапуск
процесса сбрасывает только этот режим. Его API и поведение сохранены.

## Frontend

`App` по умолчанию показывает `BlackBoxGame`, переключая его с `VaultGame`.
`useBlackBox` управляет запросами и серверным снимком. `Board` отображает
отметки, результаты портов и SVG-путь выбранного сканирования после решения.
`Rules` содержит схемы пяти случаев поведения луча. Поле имеет одну точку
входа по Tab, стрелки перемещают фокус, Enter активирует клетку или порт.
`useElapsed` дополняет серверный интервал локальным временем до открытия.

`shared/api/blackbox.ts` проверяет JSON и ID полученной сессии, поддерживает
тайм-аут 8 секунд и отмену запроса. Игровые действия блокируются на время запроса
и до восстановления неизвестного результата. Очки обновляются только сервером.

Ключ `thevault.blackbox.v1` в `localStorage` хранит ID активной сессии,
ID по датам, ID тренировки и незавершённый ответ. Перед отправкой ответа
сохраняются случайный `requestId` и клетки. При восстановлении клиент сначала
делает GET: если ID уже есть в истории ответов, повтор не нужен; иначе повторяется
тот же запрос. Без записи ID в хранилище ответ не отправляется.
Ошибка сканирования или отметки восстанавливается через GET. `404` возвращает
к выбору игры, временная ошибка сохраняет ID для следующей загрузки.

Переключатели используют `useVaultGame`, клиент `shared/api/vaults.ts` и ключ
`the-vault.session-id`. Их проверка не имеет `requestId`, поэтому после потери
ответа восстанавливается через GET без повторного POST.

## Запуск и проверки

`cmd/server` настраивает соединение, миграции, HTTP-тайм-ауты и завершение
по сигналам. Compose запускает PostgreSQL 18 с постоянным volume. Vite проксирует
`/api` на backend; раздача production-сборки остаётся отдельной настройкой.

Go-тесты проверяют трассировку, весь каталог раскладок, сессии и конкуренцию.
Интеграционные тесты с тегом `integration` создают отдельную схему в настоящей
PostgreSQL и проверяют миграции, атомарность, сохранение и HTTP-сценарии.
Vitest и React Testing Library проверяют управление обоими режимами,
валидацию ответов и восстановление незавершённых запросов. CI запускает оба
набора тестов и сборки.
